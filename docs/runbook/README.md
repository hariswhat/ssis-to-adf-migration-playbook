# Runbook

For the people running the migration and, after cutover, the nightly load.
Commands run from the repository root unless stated otherwise.

## 1. Set up an environment

1. Create the factory, Key Vault and self-hosted IR. Register the IR on a
   Windows VM that can reach ERPSQL01 and \\fileshare01.
2. Put `erp-sql-password` and `fileshare-password` in Key Vault and grant the factory's managed identity Get on secrets.
   SSIS read the ERP as the Agent service account (Windows authentication);
   the factory uses the SQL login `svc_adf_erp_reader`, which needs creating
   with read access to `dbo.customer` and `dbo.order_line`. The linked
   service requires an encrypted connection, so ERPSQL01 needs a certificate
   the self-hosted IR's VM trusts.
3. In the warehouse, create a user for the factory's managed identity and
   grant it:
   - EXECUTE on schema `etl` (the two procedures in `sql/procedures` and the
     existing `etl.usp_merge_dealer_target`);
   - SELECT on `etl.watermark` (the stage pipeline reads it; the fact
     procedure updates it through ownership chaining);
   - SELECT, INSERT, DELETE and ALTER on schema `stg` (ALTER for TRUNCATE).
   The procedures reach `dw` through ownership chaining. If Maintenance_Purge
   is kept, add DELETE on `etl.sales_rejected`.
4. Apply `sql/procedures/*.sql`. `etl.usp_merge_dealer_target` is already in
   the warehouse and is not part of this repo.
5. Deploy `adf/` (generated by `make convert`; do not edit it by hand). The
   trigger `tr_nightly` is deployed stopped.
6. Create the Azure-SSIS IR with SSISDB on the warehouse server, using
   Microsoft Entra authentication: the factory's managed identity must be an
   Entra admin of the server, or a member of a group that is. Deploy the
   NorthgateETL project to SSISDB.
7. Give the Azure-SSIS IR a path to on-premises sources: configure the
   self-hosted IR as its data proxy (this needs an Azure Blob staging linked
   service), or join it to a VNet with a route to the network. The FTP
   connection of Export_PlantExtract needs the VNet route.
8. The lifted packages connect as the factory's managed identity
   (`ConnectUsingManagedIdentity`) and run their own SQL, so for as long as
   any of them is lifted the identity also needs:
   - SELECT, INSERT, UPDATE on `dw.dim_customer` (Load_DimCustomer);
   - SELECT on `dw.dim_product`, INSERT on `dw.fact_sales` and
     `etl.sales_rejected` (Load_FactSales);
   - UPDATE on `etl.watermark` (Stage_Orders while Load_FactSales is lifted);
   - DELETE on `etl.sales_rejected` if Maintenance_Purge runs.
   Revoke each grant when the last package that needs it is rewritten.

## 2. Parallel run for a wave

See ADR-0005 for why it is set up this way.

1. Generate the parallel factory: the wave's packages rewritten, later waves
   lifted, for example for wave 2:
   `python -m playbook.convert estate/NorthgateETL --out build/adf-parallel --lift Load_FactSales --lift Maintenance_Purge`
   (Export_PlantExtract is lifted anyway; Master_Nightly is never lifted,
   because `pl_master_nightly` is the orchestrator from the first night.)
   Point its warehouse linked service and the lifted packages' DW override at
   `NorthgateDW_parallel` (open issue 6). Before deploying it to a second
   factory:
   - delete the "Run Export_PlantExtract" activity (and its alert and Fail
     activities) from its `pl_master_nightly`, so the partner gets one file;
   - set `pl_import_dealertargets`'s `inbound_folder` and `archive_folder`
     defaults to a parallel copy, for example `parallel/inbound` and
     `parallel/archive`;
   - give it its own Azure-SSIS IR and SSISDB, and share the production
     self-hosted IR with it as a linked IR.
2. Each night at 01:00, copy the warehouse to `NorthgateDW_parallel` and
   copy the night's dealer files to `parallel/inbound`, then let both
   factories run.
3. Compare each table the wave writes, by key, with the comparison in
   `playbook.reconcile`. Record the result per night.
4. Record run times from ADF monitoring next to the times of the lifted
   runs.

A night passes when the reconciliation has no unexpected differences. A
difference that is a deliberate change needs an entry in
`reconciliation/accepted.yml` with an ADR; see section 6.

## 3. Start and stop the Azure-SSIS IR

The IR is billed while it is started, whether or not a package runs.

- Start it at 01:00, before `tr_nightly` fires. It takes several minutes to
  start; check its status in the factory's Integration runtimes view.
- Stop it after `pl_master_nightly` completes.

Until this is automated (open issue 1), whoever is on call starts and stops
it. If it is left running, the cost is the node price for every hour it runs.

## 4. Cut over a wave

Preconditions: five passing parallel nights; finance has seen any accepted
differences (ADR-0004); the rollback in section 5 has been read.

1. Generate `adf/` with the wave's packages no longer in the `--lift` list,
   and deploy it. The next run uses the rewritten pipelines.
2. Watch the first night and compare row counts with the previous night.
3. Keep the parallel factory's JSON for the wave in case of rollback.

The first cutover (before wave 1) is different: deploy with every package
except Master_Nightly lifted, start `tr_nightly`, and disable the SQL Agent
job.

## 5. Roll back a wave

1. Redeploy the previous `adf/`, with the wave's packages lifted again.
2. If the rewritten pipelines loaded bad rows, the procedures are rerunnable
   (ADR-0003): fix and rerun. If SSIS is to reload the night instead, delete
   the night's fact rows for the affected order lines first, because the
   SSIS fact load appends.
3. Before wave 1 only: re-enable the SQL Agent job and stop `tr_nightly`.

## 6. When reconciliation fails

1. Look at the first differences the report lists. The usual causes:
   - behaviour the rewrite changed (collation, type 1 handling, rounding):
     compare the SSIS component's settings in the .dtsx with the procedure;
   - timing: the two factories read the ERP minutes apart;
   - duplicate or dangling keys: these are always bugs;
   - a bug in the procedure.
2. If the new behaviour is right, write or update an ADR and add a matcher
   and an entry to `reconciliation/accepted.yml`. Matchers must be narrow:
   they say exactly which differences are accepted, and each has a test that
   it rejects others.
3. Otherwise fix the procedure, add a test, and restart the count of five
   passing nights.

## 7. A night fails after cutover

1. The alert names the pipeline and activity, and the pipeline run fails
   after the alert. A failure in a child pipeline alerts twice, once from
   the child and once from the master's Execute Pipeline activity (open
   issue 16); the child's alert names the activity. Open the run in ADF
   monitoring.
2. Copy from ERP or the file share fails: check the self-hosted IR node is
   online and the Key Vault secret has not expired. Rerun from the failed
   activity; the Copy's pre-copy script truncates staging again.
3. A stored procedure fails: its transaction rolled back. Fix and rerun from
   the failed activity. The order watermark did not move, so no lines are
   lost.
4. Export_PlantExtract fails: check the IR was started (section 3), then the
   package's messages in SSISDB.
