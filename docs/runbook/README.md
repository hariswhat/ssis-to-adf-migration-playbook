# Runbook

For the people running the migration and, after cutover, the nightly load.
Commands run from the repository root unless stated otherwise.

## 1. Set up an environment

1. Create the factory, Key Vault and self-hosted IR. Register the IR on a
   Windows VM that can reach ERPSQL01 and \\fileshare01.
2. Put `erp-sql-password` and `fileshare-password` in Key Vault and grant
   the factory's managed identity Get on secrets.
3. In the warehouse, create a user for the factory's managed identity and
   grant it EXECUTE on schema `etl`, SELECT and UPDATE on
   `etl.watermark`, SELECT/INSERT/DELETE/ALTER on schema `stg` (ALTER is
   needed for TRUNCATE) and nothing else. The procedures reach `dw` through
   ownership chaining.
4. Apply `sql/procedures/*.sql`.
5. Deploy `adf/` (generated by `make convert`; do not edit it by hand). The
   trigger `tr_nightly` is deployed stopped.
6. Only while a package is lifted: create the Azure-SSIS IR, which creates
   SSISDB on the catalog server, and deploy the SSIS project to it.

## 2. Parallel run for a wave

1. Point the wave's new pipelines at a separate schema (for example `dw_new`)
   so both platforms load the same staging data side by side.
2. Run the new pipelines after SSIS each night, for at least five nights.
3. Compare each table the wave writes, by key, with the comparison in
   `playbook.reconcile`. Record the result per night.
4. Record run times from ADF monitoring next to the SSIS durations from the
   catalog's execution reports.

A night passes when the reconciliation has no unexpected differences. A
difference that is a deliberate change needs an entry in
`reconciliation/accepted.yml` with an ADR; see section 6.

## 3. Start and stop the Azure-SSIS IR

The IR is billed while it is started, whether or not a package runs.

- Start it at 01:00, before `tr_nightly` fires; it takes several minutes to
  start, so check its status in the factory's Integration runtimes view.
- Stop it after `pl_master_nightly` completes.

Until this is automated (open issue 1), whoever is on call starts and stops it.
If it is left running, the cost is the node price for every hour it runs.

## 4. Cut over a wave

Preconditions: five passing parallel nights; finance has seen any accepted
differences (ADR-0004); the rollback in section 5 has been read.

1. Disable the wave's packages in the SQL Agent job (disable the step, or set
   the Execute Package task's Disable property in Master_Nightly). Do not
   delete anything.
2. Repoint the wave's pipelines from the parallel schema to `dw`.
3. For the last wave, start `tr_nightly` and disable the Agent job.
4. Watch the first night and reconcile row counts against the previous night.

## 5. Roll back a wave

1. Stop the new pipelines for the wave (or `tr_nightly` for the last wave).
2. Re-enable the SSIS steps disabled in section 4.
3. If the new pipelines loaded bad rows, the procedures are rerunnable
   (ADR-0003): fix and rerun, or let the SSIS packages reload the night.
   Facts loaded by SSIS append, so delete the night's rows for the affected
   order lines before rerunning SSIS.

Keep SSIS able to run for a month after the wave's cutover.

## 6. When reconciliation fails

1. Look at the first differences the report lists. Three causes cover most:
   - behaviour the rewrite changed (collation, type 1 handling, rounding):
     compare the SSIS component's settings in the .dtsx with the procedure;
   - timing: the two sides read staging at different times;
   - a bug in the procedure.
2. If the new behaviour is right, write or update an ADR and add a matcher
   and an entry to `reconciliation/accepted.yml`. Matchers must be narrow:
   they say exactly which differences are accepted.
3. Otherwise fix the procedure, add a test, and restart the count of five
   passing nights.

## 7. A night fails after cutover

1. The alert names the pipeline and activity. Open the run in ADF monitoring.
2. Copy from ERP or the file share fails: check the self-hosted IR node is
   online and the Key Vault secret has not expired.
3. A stored procedure fails: the transaction rolled back. Fix and rerun the
   pipeline from the failed activity.
4. Export_PlantExtract fails: check the IR was started (section 3), then the
   package's messages in SSISDB.
